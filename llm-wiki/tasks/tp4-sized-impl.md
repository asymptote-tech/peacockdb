# tp4-sized Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the sf40 batching query set at `tp4_sized` on the H100, unfused: benchmark files, profiles,
the H100 list written at two modes, the report's tp4_sized sums, and bench-rows' page regenerated
with the tp4_sized rows.

**Architecture:** no engine or harness code. sf40-baseline's run path is repeated with the mode
filter `tp4_sized`: `scripts/env/run-gpu.sh --instance-id computeinstance-e00e6yena4nzjgaym0 --profile editor-eu` (new-hosts Task 9) builds, ships, runs and
pulls; bench-rows' trailer supplies `load_us`/`execute_us`; `create_nsys_profile.sh` with
pinned-loads' `nsys_loads.py` writes `calls.tsv`, `loads.tsv`, `hbm.tsv`. The only code change is
one entry in sf40-baseline's `H100_MODES` in `benchmark.rs`, the modes the H100's `cases.csv` is
written at; the tree check already holds the tree to that list by containers' rule (a device tree
that holds a `cases.csv` is held to it). The report is regenerated by batching-report's
`batching_report.py`, the page by bench-rows' `the_benchmark_report_matches_the_trees`.

**Tech Stack:** Rust tests (`test_corpus_goldens`), bash (`run-gpu.sh`, `create_nsys_profile.sh`),
Python (`nsys_loads.py`, `join_records.py`, `batching_report.py`).

**Spec:** `llm-wiki/tasks/tp4-sized.md`. Siblings consumed: `sf40-baseline.md` (and its plan `sf40-baseline-impl.md`, whose names this plan uses),
`new-hosts-impl.md`, `bench-rows-impl.md`, `pinned-loads-impl.md`, `batching-report-impl.md`.

## Global Constraints


- **VM time is minimal** (the human's rule, 2026-11-03). A VM starts right before its first
  remote command and stops right after its last `pull`. It is never left up across a wait: a local
  build, CI, a review, the human. Binaries are built and staged first, and the H100 starts only
  once they are ready to ship. No step leaves a VM running for a later task. Each start and stop
  goes into the detail file's `## VM time` table, in the host's local time, with the hours per VM
  for the task. The watchers (1 h idle, 4 h per process, the hourly GitHub check) are the backstop,
  not the plan.
- Device tree `testdata/benchmark-results/h100-80gb-hbm3/`; files `{tpch,tpcds}.sf40/tp4_sized.benchmark.txt`.
- Query set: every `ok` or `wrong` row of sf40-baseline's H100 `cases.csv`
  (`testdata/benchmark-results/h100-80gb-hbm3/cases.csv`, its one ordered list, read through
  `parse_device_cases` or `scripts/calibration/device_cases.py`; `skipped` rows are no case)
  whose line in the main case list carries `tp4_sized`. That covers the batching set
  (TPC-H q1-q22, every TPC-DS line) and the TPC-H micro queries, so the list's writer finds a
  tp4_sized section for every line it considers. No other mode is in scope.
- A query enabled at tp4_sized that fails at sf40 is a failed case with its reason (the harness's
  `FAILED` record, `status=failed reason=<one line>`, containers' `test_support/mod.rs:1011`), as sf40-baseline does.
- Both Nsight passes per case; derived files under `testdata/calibration/h100-80gb-hbm3/`; captures never committed. A failed capture is listed with its reason.
- Records: one per dataset, named `h100-80gb-hbm3/<ds>.sf40` (sf40-baseline's), holding both modes' rows;
  `records.sha256` keeps one line per dataset.
- The H100's watcher stops one process after 4 hours: segments with `PEACOCK_BENCH_RESUME=1`.
- H100 counters: `PCK_BENCH_HBM_SET=gh100 PCK_BENCH_HBM_PEAK_BW=3.35e12` (pinned-loads-impl.md:39).
- `testdata/benchmark-report.html` is regenerated in the commit that adds the files.
- The VM is stopped when the run ends. Never open any file under `~/.nebius/` or any `*.pem`.

## Review Focus

1. **A query in the H100 `cases.csv` whose main-list line lacks `tp4_sized`.** Today none (master's
   registry: tpch 44/44, tpcds 82/82 enabled at both modes). `bench-each.sh` does not run it, the
   writer does not consider the mode for it, and the report must not silently sum fewer queries:
   the report prints `n/N` per batch.
2. **A query that passes tp1_single and fails tp4_sized** (OOM with four lanes). Its section is
   `status=failed reason=…`; its `cases.csv` row keeps `tp1_single` only, and the report treats it
   as missing from the sum, not as zero.
3. **A resumed segment** writing a second trailer into a section: `device_tree_problem` already
   refuses two provenance sets; Task 3 Step 1 runs it.
4. **Rows of two modes in one calibration file.** tp4-sized rows join sf40-baseline's tp1-single
   rows by the `mode` column (the harness's case spelling, `tp1-single`/`tp4-sized`); a rerun must
   replace, not duplicate, tp4-sized rows (Task 2 Step 7).
5. **Multi-lane loads overlapping** (pinned-loads-impl.md "Review focus" 1): `loads.tsv`'s
   `unattributed_us` may be large at tp4; the detail file reports it, it is not a failure.
6. **The published record re-joined.** Task 2 Step 5 joins sf40-baseline's published tp1_single
   records (their free-memory token already `<min>-<max>`) with the tp4_sized segments; a dataset
   whose record loses either mode's rows is a failure.
