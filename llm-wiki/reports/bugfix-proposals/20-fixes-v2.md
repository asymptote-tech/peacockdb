## The two decisions

**#186/#188 — planner makes a limited scan one lane and one batch (F12).** Both proposals agree on the shared core (CPU `with_limit`; C++ drops `set_num_rows` and caps the table read with `cudf::slice`, since cuDF refuses `num_rows` beside `row_groups` by contract). They split on where "across batches" lives. The plan wins on the evidence:
- It is the rule `architecture.md:374-379` already states. Both designs rewrite the four `set_num_rows` sentences (`:377-378`, `:814`, `:1043`, `:1073`), because both delete `scan.cpp:61-63`; only the counter design also makes `:374-379` false and adds a `slice_handle` arm at `:763`.
- One owner. The counter design adds a `remaining` on both loaders, a `PerStraddlingBatch` `slice_handle` recipe arm, a `recipe-payloads.txt` section, and an exception arm in `a_loaders_batches_line_up_with_the_row_groups_that_made_them` (`test_corpus_goldens.rs:289-320` counts batches per lane and demands `emitted == count` under `early_exit=none`, so a loader that stops short at a rowgroup mode breaks it). Under one lane/one batch that rule holds with no arm.
- The 188 proposal's two objections fall. "Reads the whole table into one device table" — false with the prefix-of-survivors mapping (186-review F5: take `scan.groups` until cumulative `rows` ≥ limit, `partition(prefix, 1, Off)`), which bounds the decode to the row groups covering the limit at every mode; the counter design still decodes all 49 lineitem row groups at the three `Off`-batching modes (its own §7: 371 MB transient). "Unchecked for injected plans" — false: the validator (F12 3b) runs on every tree `planner::plan` sees (`pipeline.rs:37,73`); the injection's `drained` (`tests/common/injection.rs:558-572`) re-cuts only a mapping with more than one lane (`groups.len() > 1`), so a limited scan's one-lane mapping is left alone, and the `Empties` dimension wraps the executor, not the plan.
- No `slice_handle` on the loader path and no third copy of a count-and-slice rule (hacks-audit 8 already has two). Hacks-audit production bug 1 (a sliced device batch priced with no string bytes) is unreachable in the corpus under either design — the 188 proposal's §7 says a loader slice is reachable only for a limit larger than the first batch, which no query has — so it is not a discriminator.
- Cost: ten tpch plan sections (`scan-limit` and `nested-limits` at five modes — the prefix mapping moves the `Off`-batching modes too) and the restructure of `a_limit_slices_at_most_two_batches_and_stops_the_scan` (`test_cpu_end_to_end.rs:426-526`, its `most_offered > 2` guard). Golden churn, not mechanism. What it buys beyond the counter design: `nested-limits`' `part` loader stops reading 200,000 rows for 28 at every mode (`tp1-single-mini.cpu.txt`, `== nested-limits`), not only at the rowgroup ones.

**The CPU-join chunking wall is #185, retitled, and its own fix (F10).** Evidence: `tpcds.sf1/tp1-single-mini.cpu.txt:4927+` (`== q93`): the `Right` join takes one probe batch (`in_rows=[[287867],[2880404]]`, the store_sales loader `batch_rows=[[2880404]]`) and emits 36 batches; the per-batch `GpuAggregate` emits 36 partial batches totalling 7486; `GpuAggregateBatches` records `in_rows=[[7486]]`. On the device one call → one table → one aggregate batch of 7169 groups → `in_rows=[[7169]]`, which equals the merge's output — the number #185's title blamed on the merge. `in_rows` is the driver's arithmetic and is right on both engines. #185's sentence "every `batch_rows` entry agrees" was read off `line_difference` (`golden_text.rs:158-187`), which prints the first differing line only; digest B's aside that "q93's join emits 36 per-probe batches on both engines" is wrong on this evidence (one probe batch). Same shape at tpch `hash-join` (`tp1-single-mini.cpu.txt:813-814`, 733 chunks of 8192 over one probe), `cross-join` (`[[25,25,25,25,25]]`), `nested-loop-left-join` (`[[50,1]]`), `anti-join`, `semi-join`, q4 (`[0×18, 52523]` from one finish call). The fix is on the CPU side because the device side is the invariant `architecture.md` states three times ("no executor may return more than one batch per call per output lane"; "queues are self-bounding at one batch per lane"; "batch boundaries are a pure function of the plan") and `CpuExec::exec` (`cpu_backend/mod.rs:173-201`) already keeps it; relaxing the comparator would hide a real divergence, chunking on the device needs an ABI. It is not a new ticket: `cost-report` refuses a registry ticket that resolves nowhere, and #185 already resolves. Everything the device runs through a join lands on it, so F10 precedes every device registry pass and every batch of newly authored cpu sections.
