# #47 — q77 GPU returns 40 rows vs CPU 45

Read at master `188c23ce`. Paths relative to `/media/data/peacockdb`. Nothing built or run; every
number below is read off a committed golden, the code at HEAD, or the code at the commit that filed
the ticket (`git show 2d07e908:…`).

**Verdict up front.** The row loss the ticket records cannot happen in today's C++ operators: it was
two aggregate defects of the pre-split executor, both fixed the day after the ticket was filed, and
q77 was never run on a device again. The outer join the ticket suspects is exonerated at the filing
commit itself. What reading cannot close is small and named in §7, and the smallest query that
exercises it runs on a device today, in a harness that already exists, with no ticket in the way.

## 2. Root cause

**The mechanism, at the commit that measured it.** `cpp/src/plan_executor.cpp` at `2d07e908`,
`execute_aggregate` (`:1190-1400`):

- `grouping_sets` and `null_exprs` are never read. The node's `group_exprs` become a plain
  `cudf::groupby::groupby gb{keys_view}` (`:1335`) and one `gb.aggregate(requests)`. The wire
  already carried the masks — `e5d2c0e7`'s message: "the IR + serializer already carried
  GroupingSetMask/null_exprs/grouping_sets" — so the Partial over q77's union answered with **one
  grouping set of three**: the `(channel, id)` set and nothing else. On any data that loses exactly
  1 + |channels| = **4 rows** (the grand total and the three channel subtotals). The same commit's
  message files q14/q80 against "the grouping-sets gap (issue #40)" and q77 against #47 in the
  next clause — the same defect, ticketed twice.
- `groupby gb{keys_view}` takes cuDF's default `null_policy::EXCLUDE`, which drops every group with a
  NULL key: the `(catalog channel, NULL)` row, **1 row**. (Upstream, the same default drops the NULL
  `cs_call_center_sk` / `cr_call_center_sk` groups before the cross join, which changes the catalog
  sums but not the count.)

4 + 1 = 5, the number the ticket reports. On today's data that is 44 → 39, and the ticket's
40-vs-45 is what a reader counting printed lines with the header row gets from 39-vs-44; the
alternative — the sf1 data of the day had one more finest-set row (generated by an unpinned DuckDB,
since pinned because "the TPC-DS dsdgen column types drift between releases", build-test.md) — is
equally consistent and equally unverifiable. Either way the two mechanisms are the only two the
code at that commit had, and the count they lose is the count the ticket has.

**Both were fixed the next day and q77 was never re-run.** `e5d2c0e7` (2026-06-11, "GROUP BY
ROLLUP/CUBE/GROUPING SETS (#40)") added the per-set expansion; `d3c92de5` (2026-06-11, "Bucket H:
SQL null-semantics") added `null_policy::INCLUDE`. Neither is an ancestor of `2d07e908`
(`git merge-base --is-ancestor` says no). q77's device line stayed commented at `e5d2c0e7:268`,
through `9c0979f3` (the macro refactor kept it commented) and `aeb4e261` (T19 wrote `none` for its
gpu modes, `corpus_cases.inc:243`). The 40 was measured once, before the fixes, and carried.

**The outer join is exonerated at the filing commit itself.** The legacy `Right` arm
(`plan_executor.cpp:1633-1641` at `2d07e908`) is `cudf::left_join(right_keys, left_keys)` with the
pair swapped back and `out_of_bounds_policy::NULLIFY` on the left (`:1658`) — the same as today's
`cpp/src/operators/join.cpp:295-302`, `:312-320`, minus `join_nulls`. A left join preserves every
row of its first argument, which is the probe side; nothing in that arm can lose a probe row. And on
today's data it would not matter if it could: both `Right` joins match every probe row —
`tp1-single-mini.cpu.txt:3703-3704` `in_rows=[[6],[6]] … output_rows=6` (store) and `:3795-3796`
`in_rows=[[40],[30]] … output_rows=30` (web); every store and web row in the result golden has a
non-zero `returns_`, so a Right-as-Inner would drop nothing. The cross join (`:3757`, 5 × 4 = 20)
is what the ticket already cleared.

**Can the mechanism exist in today's operators? No, by reading:**

- `cpp/src/operators/aggregate.cpp:340-434` — where `null_exprs` is non-empty, one groupby per set
  over the keys with the masked positions replaced by the typed NULL placeholder
  (`build_column(agg->null_exprs()->Get(i), tv)`, `:353-354`), each with `null_policy::INCLUDE`
  (`:399`), an INT32 gid appended after the keys (`:388-392`, `:414-415`), the k results concatenated into
  one table (`:428`). The plain and Merge paths take `gb{keys_view, null_policy::INCLUDE}` (`:441`),
  so the per-lane and cross-lane merges keep NULL-keyed rows and group them.
- The placeholders are real NULLs: a `LiteralExpr` goes through `build_column`'s literal arm
  (`cpp/src/expr.cpp:830-835`) to `build_scalar`, which honours `is_null` (`:456`). #198 is the
  *AST* literal arms; a placeholder never reaches them.
- The wire puts the masks on the init alone: `wire/aggregate_writer.rs:41-72` writes `null_exprs`
  and `grouping_sets` from the body, and `planner/translator/aggregate.rs:337-356` builds every merge
  body with both empty — which is the discriminator `aggregate.cpp:337-341` reads. The plan golden
  shows it: `tp1-single.plans.txt:8163` `GpuAggregate … grouping_sets=[[], [channel@0], [channel@0,
  id@1]]` at 3 lanes; `:8162` and `:8160` the two merges on `[channel, id, __grouping_id]`.
- The rest of q77's device path cannot lose a row either: `GpuUnion` is lane relabeling
  (architecture.md, no FFI call; `tp1-single.plans.txt:8164`, recipe `:8244` "none"); the sort's `fetch=100` slices only
  past 100 rows (`sort.cpp`); `GpuAccumulateBatchesAndSort` over one batch is the concat fallback.

**What a device already proves.** `tests/test_gpu_recipe_walk.rs:748`
`a_rollup_answers_with_every_grouping_set` — the three-set ROLLUP over `lineitem`, walked at
one lane against DataFusion; `:685` `each_lane_merges_its_own_state_before_the_cross_lane_merge_folds_them`
— state merged per lane then across lanes; `tests/common/executor_cases.inc:106-110` — a merge over
state whose keys carry a grouping id, on both engines. Those cover the expansion and the merge
separately. Uncovered on a device: NULL-keyed rows merging *across lanes* (q77's grand total is
computed once per lane, 3 rows into 1, and its channel subtotals must stay 3), a natural NULL key
beside the placeholder NULL kept apart only by the gid (`aggregate.cpp:384-387` says this is the
gid's whole job), and `Right` at all — no tpch corpus query plans one (`tp1-single.plans.txt` has
zero `join_type=Right`), `tests/test_gpu_executors/join.rs` drives Inner and the semi family, and
the walk's `driven()` (`:780`) refuses Right as "a join type no shape here plans". That is the
residue §3 pins and §7 names.

## 3. Localized fix

No engine change. The ticket closes on evidence, and the evidence is one walk case plus the run that
proves it. Three files.

### `peacockdb-core/tests/test_gpu_recipe_walk.rs` — the device pin

The walk is the right instrument: it drives the plan the writer emits, exports without the unload's
sink-schema concat (so #187 cannot intervene, hacks-audit "propping up" 12 — the compare is names
plus rendered rows), and compares against DataFusion on the same SQL. Everything the new query
produces is already in `PROVEN` (`:798-809`) and `Driven::Handled` (`:770-793`): `Scan`,
`PlainProject`, `Aggregate{merge:false}`, `CoalescePartitions`, `Aggregate{merge:true}`,
`Project(Finalize)`; the union is routed by `route()` (`:494`) with no call. No new kind, so
`driven()` and `PROVEN` do not move.

- After `const ROLLUP` (`:640`), add

  ```rust
  /// q77's top in miniature: a rollup whose input is a union of lanes, so the grand total is
  /// computed once per lane and folded across them by NULL keys, and one branch carries a
  /// natural NULL beside the placeholder the subtotal puts in the same position.
  const ROLLUP_OVER_LANES: &str = "SELECT channel, id, sum(v) AS v FROM ( \
       SELECT 'nation' AS channel, n_regionkey AS id, n_nationkey AS v FROM nation \
       UNION ALL \
       SELECT 'region' AS channel, \
              CASE WHEN r_regionkey = 0 THEN NULL ELSE r_regionkey END AS id, \
              r_regionkey AS v FROM region) x \
       GROUP BY ROLLUP(channel, id)";
  ```

- Beside `a_rollup_answers_with_every_grouping_set` (`:748`), add a test whose doc names the case
  (the ticket number in the comment, never the name — coding-style.md, Names):

  ```rust
  /// Two lanes each expand the sets, so the grand total exists twice with every key NULL and
  /// the cross-lane merge must fold it to one while keeping the two channel subtotals apart;
  /// the region branch's natural NULL id sits in the same position as the subtotal's
  /// placeholder and only the grouping id separates them. Thirteen rows, or a nameable loss:
  /// ten without the expansion, nine with NULL keys excluded, twelve with the two NULLs
  /// conflated, fourteen with the totals unfolded. The shape #47 recorded a loss on.
  #[tokio::test]
  async fn a_rollup_over_a_union_folds_its_totals_across_lanes() {
      let calls = assert_walk_matches_datafusion(ROLLUP_OVER_LANES, ONE_LANE).await;
      assert_eq!(times(&calls, FbKind::Aggregate { merge: false }), 2,
          "one expansion per lane: {}", trail(&calls));
      assert_eq!(times(&calls, FbKind::Aggregate { merge: true }), 3,
          "a merge per lane and one across them: {}", trail(&calls));
      assert_eq!(finalizing(&calls, FbKind::Aggregate { merge: true }), 1,
          "the finalize runs once, above the cross-lane merge: {}", trail(&calls));
  }
  ```

  `assert_walk_matches_datafusion` already refuses an empty answer (`:586-589`), so the
  thirteen rows are compared rather than vacuously agreed. The row count is not asserted as a
  literal — the DataFusion compare is the exact claim and the numbers in the doc are what a
  reader turns a failure into.

- The coverage list at `:818-828` gains `(ROLLUP_OVER_LANES, ONE_LANE)`, so
  `the_kinds_a_device_has_run_are_the_kinds_this_file_claims` sees the same set the tests run.

Why this SQL: `nation` and `region` are one row group and under `SMALL_TABLE_BYTES`, so every mode
gives each branch one lane and one batch — the union makes the lanes (2), not the planner, which is
q77's `GpuUnion: lanes=3` at tp1 (`tp1-single.plans.txt:8164`). Integer keys and measures (`n_regionkey:Int32`,
`sum → Int64`) and a literal-only string column, so neither #187 nor #183 is reachable even under
the driver; no join, so #152 is not. The CASE is the only way TPC-H yields a NULL key (the data has
none), and it is safe: `is_ast_able` routes every CASE to `build_column_case` (`expr.cpp:403-407`),
whose `then` arm is the literal path above, not #198's.

## 4. Alternatives rejected

- **Enable `gpu_tp1_single` for q77 now.** Refused at the unload by #187 before any comparison, and
  the panic in `corpus_gpu.rs:94` drops the per-node report, so the run shows nothing.
- **Walk q77 itself.** Needs a tpcds context (`test_gpu_recipe_walk.rs:536` registers tpch) and
  `driven()` admitting `Right` and a one-batch `CrossJoin` — task 13's re-classification; the
  minimal query proves the class without waiting for it.
- **A corpus query for the minimal SQL.** Its device cell would be red on arrival at the merges
  (#185, `GpuAggregateBatches` `in_rows`), and its cpu cells add nothing `tpch/rollup_over_join`
  does not already pin.
- **A C++ gtest for grouping sets.** Proves the operator against a hand-built buffer, not the
  buffer the writer emits; the walk does both.
- **Fix the gid's type/encoding "while here".** #65's, invisible at tp1, and a hash-placement
  question at tp4 behind #189 — a different ticket's evidence.
- **Close by reading alone.** The cross-lane NULL-keyed fold and the gid separation are what the
  ticket's number rests on, and no device test has run either; a ticket retired on an argument is
  the shape this one already had once.

## 5. Minimum corpus query

The `ROLLUP_OVER_LANES` SQL above, tpch sf1 schema:

```sql
SELECT channel, id, sum(v) AS v
FROM (
  SELECT 'nation' AS channel, n_regionkey AS id, n_nationkey AS v FROM nation
  UNION ALL
  SELECT 'region' AS channel,
         CASE WHEN r_regionkey = 0 THEN NULL ELSE r_regionkey END AS id,
         r_regionkey AS v FROM region
) x
GROUP BY ROLLUP(channel, id)
```

Plans today at every mode (both branches one lane and one batch; the union 2 lanes; the init at 2
lanes; a per-lane merge; the cross-lane merge with the finalize; a project dropping the gid — q77's
`tp1-single.plans.txt:8156-8164` with two branches instead of three). Runs at `tp1-single` and
`tp1-rowgroup` on both backends; refused at the three tp4 modes on the CPU at the top scatter,
`hash=[channel, id, __grouping_id]` with `__grouping_id:UInt8` (#189, the same as
`rollup_over_join` and q77). The device run is the walk at `ONE_LANE`, which is the tp1-single shape.

Correct answer: 13 rows — nation ids 0..4 (5) + subtotal, region ids NULL,1,2,3,4 (5) + subtotal,
grand total. What each mechanism would return instead: **10** with no grouping-set expansion (the
#40 half of the ticket), **9** with NULL keys excluded on top of that (the `EXCLUDE` half — the
natural `(region, NULL)` goes too), **12** if the natural NULL and the subtotal's placeholder NULL
merge (the gid failing at its one job), **14** if the two lanes' grand totals do not fold.

The natural-NULL form, tpcds sf1, if a reader wants no CASE: `store` and `call_center` with
`s_closed_date_sk` / `cc_closed_date_sk` as `id` and `s_number_employees` / `cc_employees` as `v`
— same plan shape, NULL for every open store or call center; it needs the walk's context to take
a dataset, which is why the tpch form is the one proposed.

For the `Right` residue (§7), the one-line tpch form: `SELECT n_name, r_name FROM nation LEFT JOIN
(SELECT r_regionkey, r_name FROM region WHERE r_regionkey < 3) r ON n_regionkey = r.r_regionkey` —
DataFusion builds on the filtered side and the translator's swap makes it `Right`; 25 rows, 10 with
a NULL `r_name`, 15 if the join were Inner. Check `join_type=Right` on the plan before trusting it;
it runs in the walk once task 13 admits `Right`. `175-proposal.md` §5 shape (b) is the q77-shaped
version with `sum` replaced by `count(*)` to stay clear of #187.

## 7. Risks and unknowns

- **Not run.** The cross-lane fold of NULL-keyed rows and the gid's separation of a natural NULL
  from a placeholder are read off `aggregate.cpp:399,441` and cuDF's groupby contract, not
  measured. The proposed test is the measurement; its first shad-gpu run is what closes the ticket.
- **`Right` on the current device executor has never run under a test.** The C++ arm is unchanged
  since the filing commit, but `gpu_backend/join.rs` around it is new. Not q77's row loss (§2), but
  the ticket's suspicion, and it stays open until the §5 one-liner runs — task 13's admission of
  `Right` is the gate.
- **The 45 and the 40 cannot be reconstructed.** Two readings fit (header line counted; data of the
  day had one more row); both give the same two mechanisms.
- **The gid is INT32 on the device and `UInt8` in the plan, with the bits reversed** — DataFusion
  sets bit `n−1−i` for a masked position (`datafusion-physical-plan-45.0.0/src/aggregates/mod.rs`,
  the `__grouping_id` tests: `a` masked → 2), `aggregate.cpp:392` sets bit `i`. Invisible at tp1
  (the finalize project drops it before the unload; a merge key's type does not change a group).
  Visible at tp4, once #189 lets the CPU hash `UInt8`: the top scatter places subtotal rows by a
  hash of different values on the two engines, so the device tier's `batch_rows` at the emitter
  goes red on q77, q5, q80 and `rollup_over_join`. #65's text should say this; it currently says
  "unobservable while no enabled query projects `GROUPING()`".
- **q77's device cell will not be clean after #187 for reasons that are not #47's**: #185 at both
  merges, and the byte-exact section compare against a CPU that chunks join output (the store_sales
  Inner join is 8 batches at `:3737-3738`, the cross join 5 at `:3757-3758`) where the device emits one table
  per call. #185's own text says q93's batch lists agreed at tp1-single, which I cannot reconcile
  with today's q93 section (36 batches out of its `Right` join, `tp1-single-mini.cpu.txt:4953-4954`); either the note predates
  a regeneration or the device does something the code does not show. A q77 run will say which.
  Neither is this ticket's.
