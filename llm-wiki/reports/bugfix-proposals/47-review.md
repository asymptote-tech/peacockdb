## 1. Verdict

**Needs changes (small).** The diagnosis is right and checks out line by line — the row loss is the
pre-split executor's missing grouping-set expansion (4 rows) plus cuDF's default `EXCLUDE` (1 row),
both fixed on 2026-06-11 by `d3c92de5` and `e5d2c0e7`, neither an ancestor of the filing commit

5. **The CASE is a confound the proposal does not name.** Minor. No device test today evaluates a
   search-form CASE with a typed-NULL `then` arm through the recipe wire: no enabled device corpus
   cell carries a CASE (the tpch/tpcds queries with one — q8, q12, q14, q93 — have every gpu cell
   off), and the one gtest that drives a CASE on a device, `PlanExecutor.ProjectSqrtThroughTheColumnPath`
   (`cpp/tests/gpu/test_plan_executor.cpp:718`), has non-null arms. The path is
   `is_ast_able` → false (`expr.cpp:406`) → `build_column_case` (`:773`) → `build_column` on the
   `then` → the literal arm (`:830`) → `build_scalar` honouring `is_null` (`:456`) →
   `copy_if_else` over an all-null INT32 column. That reads correct, but if the new test reddens, the
   CASE is the first thing to rule out, and the doc comment's four named losses would not name it.
   Two options, either fine: keep the CASE and say so in the doc (one line), or replace the region
   branch's id with `CAST(NULL AS INTEGER)`, which DataFusion folds to a bare `Int32(NULL)` literal
   and the device evaluates by the literal arm alone — the natural NULL still sits beside the
   placeholder in the same position, and the losses become 9 → 6 / 5 / 8 / 10. The CASE form tests
   more (a lane holding NULL and non-NULL ids together), so keeping it with the sentence is the
   better trade.
