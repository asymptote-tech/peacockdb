## The verdict

**Conditional go, in all four headline cells.** Every band straddles 2×. Only one of the four
mid values is above 2. By the rule fixed before any number existed, a band that straddles 2× is a
conditional go, settled by the measurement at the top of its sensitivity table. Source:
[`cost.md`](../artifacts/comet-research/cost.md) "Headline cells", generated by
[`cost_model.py`](../artifacts/comet-research/cost_model.py).

The headline cell is batch "all", against the faster CPU baseline, at parity with eight 16-core
nodes, with data read over the NIC. The faster baseline is Comet's concurrent run. For TPC-H it
was measured from S3. For TPC-DS it is a modelled S3 time (124.4 s [87.5-161.1]): the spec's
matrix ran TPC-DS concurrently only from RAM, so its S3 penalty is scaled from TPC-H's.

| dataset | size | batched ratio [band] | sharing | device | verdict |
|---|---|---|--:|--:|---|
| TPC-H | sf40 (42 GB) | **1.88** [0.52-12.88] | 2.38 | 0.79 | conditional go |
| TPC-H | sf200 (212 GB, first size past host RAM) | **1.38** [0.23-13.40] | 2.62 | 0.52 | conditional go |
| TPC-DS | sf40 (15 GB) | **2.06** [0.55-13.32] | 2.42 | 0.85 | conditional go |
| TPC-DS | "1 TB": 1,000 GB compressed, about SF2,600 (first size in the grid past host RAM) | **1.44** [0.06-22.98] | 3.74 | 0.38 | conditional go |

Sizes in the model are compressed Parquet bytes, so "1 TB" is about SF940 for TPC-H and SF2,600
for TPC-DS, not SF1000 (from the sf40 footers).

- **The one-pass floor is below 1.** On eight 16-core nodes at sf40, the median per-query ratio
  is 0.89 [0.34-11.94] for TPC-H and 0.90 [0.33-9.11] for TPC-DS. The worst query is 0.42 and
  0.23 ([`cost.md`](../artifacts/comet-research/cost.md) "Ratio tables"). One query alone, read
  from S3, costs more on the GPU node than on the CPU cluster. For TPC-H the local time per
  query is the faster of a cold and a warm run, while the S3 time is one cold run. That
  favours the GPU slightly.
- **The gain comes from batching, not from the GPU.** The ratio is the sharing factor times the
  device factor. The device factor is below 1 in every headline cell (0.38-0.85): reading alone,
  the GPU node is slower per dollar than Comet's concurrent run. Shared scans (sharing 2.38-3.74)
  carry the ratio to about 2. Against Comet's sequential run the sf40 device factors are above 1
  (1.17 TPC-H, 1.25 TPC-DS). In these cells, modelled for 8 × 16, the sequential CPU time is
  about 1.5× the concurrent one for both datasets (2.78/1.88 and 3.02/2.06)
  ([`cost.md`](../artifacts/comet-research/cost.md)).
- **A CPU that shared scans too would close most of the gap.** Given the same shared scans, the
  CPU baseline moves the four mids to 1.76, 1.23, 1.84 and 1.00 (modelled;
  [`cost.md`](../artifacts/comet-research/cost.md) "CPU with shared scans").
- **These numbers were revised after the audit.** The two S3 sequential runs had timed their
  plan dumps inside the batch (10.7 s for TPC-H, 69.7 s for TPC-DS). They now use the sum of
  their per-query times, which excludes the dumps. That moved the TPC-DS cells from 2.14 and 1.58
  to 2.06 and 1.44. The TPC-H mids did not change
  ([`audit.md`](../artifacts/comet-research/audit.md) finding 1).

**The settling measurements** (the top row of each cell's sensitivity table; break-even from
[`design.md`](../artifacts/comet-research/design.md) section 1):

| cell | input | value used | mid reaches 2 at | how to measure it |
|---|---|---|---|---|
| TPC-H sf40 | `shuffle_rate_gpu_node` | 4 GB/s (modelled) | 4.6 GB/s | Comet on 16 cores of the CPU VM: shuffle write and read time per GB. No GPU needed |
| TPC-H sf200 | `shuffle_rate_gpu_node` | 4 GB/s (modelled) | 9.6 GB/s | the same; above about 8 GB/s it needs lz4 on the GPU |
| TPC-DS sf40 | `scheduler_share` | 0.25 (modelled) | already 2.06; falls below 2 above 0.28 | per-stage scheduling gaps on a 16-core executor, same run |
| TPC-DS "1 TB" | `size_exponent` | 0.7 (modelled) | 0.88 | Comet at sf40 and at a second scale factor on the same CPU VM |

So three of the four cells are settled by one cheap CPU-only run, Comet on 16 cores. The fourth
is settled by a CPU run at a second data size. For TPC-DS "1 TB" the next rows are the shuffle
rate (9.1 GB/s) and the H100 VM's S3 rate (4.5 GB/s). The modelled TPC-DS concurrent S3 time
cannot lift that cell to 2 within its range: it reaches 1.94 at the range's top, 161.1 s.

**What a reader must know before trusting these numbers:**
- **"Local" means RAM-resident.** The CPU VM has one disk, a 100 GiB network disk that reads at
  0.06 GB/s (measured, [`s3/summary.tsv`](../artifacts/comet-research/measurements/s3/summary.tsv)).
  Data and Spark's shuffle and spill went on a tmpfs, so the "local" runs read RAM. That is the
  strictest CPU baseline, stricter than page-cache warm.
- **Departures from Comet's benchmark config and the recipe.** The base is Comet's own TPC
  config with the single-executor deviations in
  [`comet-internals.md`](../artifacts/comet-research/comet-internals.md) "Recipes" 3: one
  executor on 128 cores, driver 16g, heap 64g, overhead 48g, 256 shuffle partitions, and the AWS
  profile credentials provider, which Comet's native S3 reader requires. On top of that:
  - `spark.memory.offHeap.size=256g` (the recipe said 320g; 2 GB per core, Comet's own ratio),
    to fit RAM next to the tmpfs;
  - `spark.cleaner.periodicGC.interval=5min`, so shuffle files on tmpfs are cleaned between
    queries;
  - Spark's local dirs (shuffle and spill) on tmpfs, not on local disk;
  - `spark.comet.explain.fallback.enabled` and Comet's explain provider on in every run, for the
    fallback lists;
  - a q1 warm-up only in the TPC-H S3 sequential run; every other run had no warm-up query;
  - the two S3 sequential runs also dumped plans. Each query's own time excludes its dump, but
    the batch row included it, so the model uses the per-query sums (the audit's finding 1).
- **Only a share of `scheduler_ms` counts.** The event-log metric sums per-stage gaps over
  stages that run in parallel, so it can exceed a query's wall time (TPC-H q8: 7.1 s of gaps in a
  2.9 s query). The model charges a modelled share, 0.25 [0-1], capped per query
  ([`cost.md`](../artifacts/comet-research/cost.md) "The model").
- **Every NIC rate on the GPU and small-node side is an assumption.** Nebius states no NIC rate
  for any VM used here ([Nebius VM types](https://docs.nebius.com/compute/virtual-machines/types.md),
  accessed 2026-11-04). The H100 VM gets 10-100 Gbit/s (1.25-12.5 GB/s), 16-vCPU nodes 6.25-32
  Gbit/s, 8-vCPU nodes 3.125-16 Gbit/s, all tagged `modelled`
  ([`data-path.md`](../artifacts/comet-research/data-path.md) "Rates for the cost model").
- **No GPU ran.** By the human's decision there were no peacockdb runs. GPU compute is
  benchmark-minimal's measured H100 time for TPC-H q1, q3, q6, q8 and a modelled speedup band
  for everything else.
- **TPC-DS q9, q10, q14 and q35 fall back in Comet:** Spark runs part of each (a struct-typed
  project; an existence join and a count merge; a decimal AVG at maximum precision). Every other
  query in both lists runs in Comet end to end (`plans/*/fallbacks.tsv`;
  [run state](../tasks/comet-research-detail.md) "Task 4", Step 0).
- **Nothing was skipped, cut, out of memory or with a scan mismatch.** All nine configurations
  and both calibration passes ran to rc 0
  ([`skipped.tsv`](../artifacts/comet-research/measurements/comet/skipped.tsv) has only its header).

## The cost model and its inputs

Full text, tables and every input: [`cost.md`](../artifacts/comet-research/cost.md). It is
generated by `python3 cost_model.py > cost.md`, never by hand.

**Ratio** = CPU cost per query ÷ GPU cost per query. At the human's parity, one H100 node (16
vCPU, 200 GB, $4.50/h), one 128-core node, eight 16-core nodes and sixteen 8-core nodes all cost
the same per hour. So the ratio is CPU seconds ÷ GPU seconds. A tier at another price scales it by
$4.50 over that price.

**GPU side**, one H100 node, per query or per batch:

    T_gpu = overhead + max(wire / rate(tier), wire / decode_rate, compute) + shuffle / shuffle_rate + cpu_part

- `overhead` is the measured `driver_ms` plus a modelled share of `scheduler_ms`. A batch pays a
  modelled `overhead_overlap` of the sum.
- `wire` is the measured scan bytes. A batch reads the union of its queries' columns once, from
  the sf40 Parquet footers.
- `compute` is the H100 time measured in benchmark-minimal for TPC-H q1, q3, q6, q8. Elsewhere it
  is Comet's time × the GPU-eligible fraction ÷ a speedup band of 3.4-28.3×.
- `shuffle` stays on Comet's CPU path (Arrow IPC and lz4) on 16 cores. One node shuffles inside
  the box.
- `cpu_part` is what [`split.md`](../artifacts/comet-research/split.md) leaves on the CPU, run on
  16 cores instead of 128.

**CPU side**, from the 1 × 128 measurements. Eight 16-core and sixteen 8-core nodes are modelled
from them: the same work, a cluster overhead, an S3 penalty that shrinks with more aggregate
bandwidth, and shuffle over the nodes' NICs.

**Sizes.** Bytes scale with size. Work on both sides scales as size^0.7 [0.5-1.0], from Comet's
published runs. Spill sets in where one query's shuffle per node exceeds executor memory (CPU) or
host RAM (GPU, which has no spill today).

**Band.** The min and max over every corner of the inputs' low and high ends. Tags: `measured`
means a file under [`measurements/`](../artifacts/comet-research/measurements/); `published`
means a source document, including earlier in-repo reports; `modelled` means an assumption or a
derived estimate. A test rejects any other tag.

## 1. Prior art

Summary of [`prior-art.md`](../artifacts/comet-research/prior-art.md).

- **Nobody has built, forked or proposed a GPU or hardware backend for Comet.** Comet's tracker
  has no GPU issue, PR or discussion
  ([issues](https://github.com/apache/datafusion-comet/issues?q=GPU), accessed 2026-11-04). Its
  1.2.0 README says "no GPUs, FPGAs, or other specialized accelerators are required"
  (`README.md:49-51` @ab46419f).
- **The closest attempt stopped early.** Auron PR #1001 bridged a DataFusion-based Spark engine to
  libcudf. It covered scan, filter and project only, and was closed as stale on 2025-12-05
  ([PR](https://github.com/apache/auron/pull/1001), accessed 2026-11-04).
- **The nearest seam in Comet** is the Native Executors epic #7288 (opened 2026-10-28). It passes
  "only proto bytes, a partition index, input streams and config", and returns an output stream
  ([#7288](https://github.com/apache/datafusion-comet/issues/7288), accessed 2026-11-04).
- **Spark accelerators.** spark-rapids is mature and sold. Gluten with Velox-cuDF is
  experimental, and its table scan stays on the CPU by default
  ([Gluten GPU doc](https://github.com/apache/gluten/blob/d64a51dfd01bbe1b8e4adb6c1f74331fb75f531f/docs/backends/velox/get-started/VeloxGPU.md),
  accessed 2026-11-04). Photon is CPU-only. Speedata (ASIC), NeuroBlade and DualBird (FPGA) are
  vendor plugins with vendor-only numbers. The full table is in prior-art.md section 3.
- **How each feeds its device.** spark-rapids builds host buffers in the JVM and decodes on the
  GPU; UCX shuffle is opt-in. Gluten-cuDF decodes on the CPU and names shuffle read as its
  bottleneck. Theseus cut its cloud runtime 75% by replacing its S3 client
  ([arXiv 2508.05029](https://arxiv.org/html/2508.05029v1), accessed 2026-11-04). Scan and I/O
  decide the result, not compute (prior-art.md section 4).
- **Published GPU cost wins against CPU-native engines run 1.1-2.9×.** That straddles 2×, and no
  study compares a GPU with Comet. The AWS EMR G7 study shows 1.42-1.54× against Spark, not Comet
  ([AWS blog](https://aws.amazon.com/blogs/big-data/gpu-accelerated-apache-spark-with-amazon-emr-and-nvidia-rtx-pro-4500-on-amazon-ec2-g7-instances-runs-up-to-3-7x-faster/),
  accessed 2026-11-04). Theseus against Photon at cost parity: 1.12× at SF1k, 4.1× at SF30k
  ([arXiv 2508.05029](https://arxiv.org/html/2508.05029v1), accessed 2026-11-04).
- **Evidence against:** Voltron Data (Theseus) shut down
  ([Pavlo's 2025 retrospective](https://www.cs.cmu.edu/~pavlo/blog/2026/01/2025-databases-retrospective.html),
  accessed 2026-11-04). Gluten removed Intel IAA after "not yet observed performance gains"
  ([Gluten IAA doc](https://gluten.apache.org/docs/v1.4.0/get-started/VeloxIAA.html), accessed
  2026-11-04). spark-rapids dropped its CPU-scan hybrid for lack of use
  ([#15847](https://github.com/NVIDIA/cudf-spark/issues/15847), accessed 2026-11-04). NVIDIA
  tells engine builders to use the Velox cuDF backend
  ([NVIDIA FAQ](https://perspectives.nvidia.com/cudf/faq/we-want-to-add-a-gpu-execution-path-to-our-existing-query-engine-but-don-t-want-to-fork-the-mainline-6627a6/),
  accessed 2026-11-04).
- **The CPU baseline keeps moving.** Comet 1.2.0 ran TPC-DS SF1000 2.51× faster than Spark 4.1.3
  and 2.04× faster than Spark 4.2.0
  ([PR #7444](https://github.com/apache/datafusion-comet/pull/7444), accessed 2026-11-04).
- **`spark-plugin.md`'s leads were re-checked** at current versions: Comet is CPU-only;
  Gluten-cuDF passes 48 of 103 TPC-DS SF1 queries with fallback off; spark-rapids' native-reader
  epic is still open; its hybrid scan was removed; Comet's in-memory cache is experimental. All
  hold (prior-art.md "Method and versions"). This report relies on no fact taken from
  spark-plugin.md alone.

## 2. Comet's infrastructure

Summary of [`comet-internals.md`](../artifacts/comet-research/comet-internals.md). Every code
fact is at `ab46419f`.

- **DataFusion-based.** Comet 1.2.0 runs DataFusion 55.2.0 and arrow-rs 59.2.0 natively, with
  Spark 4.1.3 as its default build (`native/Cargo.toml:41-51`, `pom.xml:84`).
- **Where the plan is decided.** `CometSparkSessionExtensions` adds rules to Spark's physical
  planning. `CometScanRule` swaps Parquet scans for `CometScanExec`; `CometExecRule` walks
  bottom-up and maps Spark operators to Comet serdes (`CometRule.scala:170`,
  `CometExecRule.scala:108-147`). An operator converts only if all its children are native.
  Otherwise it stays in Spark, tagged with a fallback reason (`CometExecRule.scala:1144-1199`).
- **How the plan reaches executors.** The IR is protobuf (proto3), seven files under
  `native/proto/src/proto/`. The unit is one native block (a maximal native subtree between JVM
  boundaries), run once per Spark task. Each task injects its own file list into the block and
  calls `Native.createPlan`; Rust builds a DataFusion plan and runs partition 0 only
  (`CometExecRDD.scala:135-142`, `jni_api.rs:1536-1564`). Expressions are `Expr` trees with
  Spark semantics as flags (`EvalMode` LEGACY/TRY/ANSI).
- **Data in, shuffle, results out.** Parquet is read natively through `object_store`, with no JVM
  decode. Native shuffle writes compressed Arrow IPC (lz4 by default), one file per map task.
  Results leave over the Arrow C Data interface (`jni_api.rs:1197-1216`). Broadcasts are decoded
  and the hash table rebuilt in every task (`CometBroadcastExchangeExec.scala:296-313`).
- **Memory.** Comet requires Spark's off-heap mode. Its pool calls into Spark's
  `TaskMemoryManager` over JNI. Native operators spill themselves; Spark cannot make them spill
  (`memory_management.md:316-322`). GPU memory would sit outside all of this (estimate).
- **Scan parity.** 1.2.0 has no `spark.comet.scan.impl`. A V1 Parquet scan is either Comet's
  native scan or Spark's own, so local and S3 runs use the same scan
  (`CometExecRule.scala:457-460`). The dumped plans confirm it: no scan row in any
  `fallbacks.tsv`, local or S3.

## 3. Injecting a GPU executor

Summaries of [`comet-internals.md`](../artifacts/comet-research/comet-internals.md) "The GPU
seam", [`translatability.md`](../artifacts/comet-research/translatability.md) and
[`split.md`](../artifacts/comet-research/split.md).

**The seam.** A GPU executor fits at one place: the native step that turns a task's protobuf
into a plan, `PhysicalPlanner::create_plan` (`planner.rs:1626`). It receives the prost-decoded
`Operator` with the task's file list already injected, plus the task's Arrow inputs. It returns a
DataFusion 55 `SendableRecordBatchStream`, which Comet hands to the JVM over the C Data interface
unchanged. There is no plug-in point: the operator registry is a private compile-time singleton
(`operator_registry.rs:32-123`). So this means a fork of Comet's native crate, pinned to one
release. A JVM-side block swap is possible but leans on `private[spark]` classes (estimate).

**Are Comet plans translatable? Yes, at the operator level.** Over the 104 final plans (TPC-H
q1-q22 and the 82 TPC-DS queries, sf40, 2026-11-04, cpu128), classed against peacockdb's node set
by [`plan_census.py`](../artifacts/comet-research/scripts/plan_census.py):

| | supported | adaptable | missing |
|---|--:|--:|--:|
| operators | 2,647 | 2,374 | **0** |
| expressions and aggregates (26,944) | 93.2% | 6.7% | 20 (0.07%) |

- The 20 missing expressions sit in five queries: a runtime bloom filter (TPC-H q2, q20), a
  struct (TPC-DS q9) and a JVM codegen UDF (TPC-DS q24, q99).
- "Adaptable" is the real work: Spark's ANSI arithmetic and decimal typing (1,625 expressions
  carry `eval_mode: ANSI`), Spark's aggregate buffer layout, sort-merge joins run as hash joins,
  and three new sources (Parquet per task from an object store, Arrow from the JVM, Comet shuffle
  blocks).
- The list is biased toward translatability: the 82 TPC-DS queries leave out the window queries.

**The DataFusion gap costs little** if the translator reads Comet's protobuf, not a DataFusion
plan. The two engines then meet only as Arrow over the C Data interface. DataFusion 45 is not
used on this path at all. Reading DataFusion 55's plan instead would mean moving peacockdb's
planner ten major versions (estimate; translatability.md "What the DataFusion gap costs").

**Splitting the plan.** The rule works inside one native block: the GPU takes the largest subtree
grown from the leaves in which every operator and expression is supported or adaptable. The CPU
runs the rest from its Arrow output, with one device-to-host crossing per block.

| on the GPU | on the CPU |
|---|---|
| Parquet decode, filter, project, Spark-exact arithmetic (errors raised on the CPU) | object-store reads into pinned host buffers |
| hash joins, sort-merge joins run as hash joins | shuffle encode, compress and write; shuffle read and decode |
| partial and final aggregates, in Spark's buffer layout | broadcast decode; JVM sinks; Spark operators Comet did not convert |
| sort, top-N, limit; Spark murmur3 partition ids for shuffle | operators with a missing expression; small blocks (estimate) |

Applied to the dumped plans, 96 of 104 queries put every native operator on the GPU. The other
eight keep 2-29% of their operators on the CPU (`plans/eligible.tsv`). The fraction counts
operators, not time.

**GPUs and tasks.** One Spark executor per GPU node, with all 16 cores and
`spark.executor.resource.gpu.amount=1`. spark-rapids requires one GPU per executor
(`GpuDeviceManager.scala:162-170` @ce634969). Up to 16 tasks then share the device behind a
semaphore, as spark-rapids' `GpuSemaphore` does. peacockdb runs one query per process today, so
concurrent sessions on one device are new work.

### How far the NIC already limits Comet on CPU (Experiment 2, measured)

### Where the GPU stalls

At the inputs' values, sf40, one TPC-H query alone ([`cost.md`](../artifacts/comet-research/cost.md)
"Where the GPU stalls"): below the stall rate the wire is the slowest term.

- With decode at 4.1 GB/s, 19 of 22 queries stall below **4.1 GB/s (32.8 Gbit/s)**. That is the
  decode rate: above it the reader, not the NIC, is the limit. q14, q15 and q16 stall below 1.5-2.9
  GB/s, since compute dominates them.
- 4.1 GB/s is an H200 figure (benchmark-minimal's load times), used for the H100 and tagged
  `modelled`. If decode is bound by memory bandwidth, the H100's is about 0.7× of it, near 2.9
  GB/s (estimate). The batched headline cells do not move: at 1.25 GB/s the wire binds first.
- With decode at its high end (18.8 GB/s, GB10's chunked reader), stall rates spread from 1.5 to
  18.8 GB/s by query shape. Join and scan shapes (q3, q8, q17, q19) need the most.
- At the H100's assumed 1.25 GB/s × 0.89, every query is wire-bound.
- peacockdb's reader today, about 3.9 GB/s compressed on q6 (1.54 GB of footer bytes in 398
  ms on the H200; [`inputs.tsv`](../artifacts/comet-research/inputs.tsv) `decode_rate`), is
  slower than a 40 Gbit/s NIC. The reader has to get faster before the NIC is the question.

### Getting more out of the wire

From [`data-path.md`](../artifacts/comet-research/data-path.md) section 3.

- **Compressed transfer** already happens: Parquet crosses the wire compressed for CPU and GPU
  alike. The GPU question is decode speed. H100 has software decompression only; B200's hardware
  engine outputs 117 GB/s Snappy ([arXiv 2512.02189](https://arxiv.org/html/2512.02189),
  accessed 2026-11-04).
- **Column and row-group pruning** cuts bytes equally for both sides (estimate). Measured here:
  TPC-H q6 reads 0.15 of its projected columns' footer bytes.
- **Local NVMe as a cache** speeds repeated reads on CPU engines: Fabric "up to 60%"
  ([Fabric intelligent cache](https://learn.microsoft.com/en-us/fabric/data-engineering/intelligent-cache),
  accessed 2026-11-04).
- **Shuffle volume** is large: one sf40 pass shuffles about as many bytes as it scans (measured
  above). One H100 node shuffles inside the box, but through 16 cores. That is why the shuffle
  rate tops the TPC-H sensitivity tables.

### Caching in RAM

- **Possible, but not in Spark's cache.** Spark's `CacheManager` lives in one application's
  `SharedState`, so separate spark-submit jobs share nothing
  ([SharedState.scala](https://github.com/apache/spark/blob/master/sql/core/src/main/scala/org/apache/spark/sql/internal/SharedState.scala),
  accessed 2026-11-04). Comet's Arrow cache is "experimental and disabled by default", stored in
  JVM heap chunks (`in-memory-cache.md:28` @ab46419f).
- **Measured: Comet's own cache bought nothing here.** With the TPC-H tables cached first, the
  local runs took 53.3 s sequential and 36.1 s concurrent, against 53.2 s and 36.1 s (the mean of
  two runs) without it (cpu128, 2026-11-04 04:27-04:30,
  [`summary.tsv`](../artifacts/comet-research/measurements/comet/summary.tsv)). The data was
  already in RAM.
- **A GPU cache must live in the native executor** (pinned host RAM, then VRAM), outside Spark's
  BlockManager, and one long-lived application has to hold it (design claim, estimate).
- **RAM per GPU is about 200-320 GB on every cloud** (Nebius H100 200 GB, p5.4xlarge 256 GiB,
  a3-highgpu-1g 234 GB, NC40ads 320 GiB) and on a DGX H100 (data-path.md sections 2 and 6). Stock
  on-prem servers do not have more RAM per GPU. So the plugin is not on-prem-only, but the H100
  node's 200 GB holds at most about sf190 of TPC-H or sf520 of TPC-DS, compressed (1.06 and 0.38
  GB per SF, from the sf40 footers in
  [`footers/sf40.tsv`](../artifacts/comet-research/measurements/footers/sf40.tsv)).
  data-path.md's 0.38 GB per SF for TPC-H came from the repo's sf1 files, which compress
  differently, so its "near SF390" for host RAM is about 2.8× too high for TPC-H.

### Data on locally attached SSD (desk only)

- **Storage-optimized CPU shapes get 1.3-3.8× their NIC from local NVMe; single-GPU shapes about
  0.5× or unpublished.** For example AWS i4i.4xlarge reads 2.8 GB/s against a 1.17 GB/s baseline
  NIC, while GCP a3-highgpu-1g's two drives read 1.4 GB/s against 3.1 GB/s of NIC. The i4i
  read rate is from AWS's launch blog
  ([AWS I4i](https://aws.amazon.com/blogs/aws/new-storage-optimized-amazon-ec2-instances-i4i-powered-by-intel-xeon-scalable-ice-lake-processors/)),
  its NIC from the specs ([AWS storage specs](https://docs.aws.amazon.com/ec2/latest/instancetypes/so.html)),
  the GCP figures from [GCP local SSD](https://docs.cloud.google.com/compute/docs/disks/local-ssd);
  all accessed 2026-11-04. Full table in data-path.md section 2.
- **GDS on cloud VMs runs in "compatibility mode"**
  ([GDS release notes](https://docs.nvidia.com/gpudirect-storage/release-notes/index.html),
  accessed 2026-11-04), which falls back to POSIX reads through host memory
  ([GDS O_DIRECT guide](https://docs.nvidia.com/gpudirect-storage/o-direct-guide/index.html),
  accessed 2026-11-04). NVMe straight to the GPU is bare-metal only.
- **Capacity and loss.** Local NVMe is erased when the VM stops on AWS, GCP, Azure and Nebius
  ([AWS instance store](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instance-store-lifetime.html),
  accessed 2026-11-04; data-path.md section 4). Refilling p5.4xlarge's 3.84 TB from S3 takes about
  5-7 minutes (estimate).
- **In the model** the local NVMe tier buys nothing at its price: p5.4xlarge's drive gives 1.49
  (TPC-H) and 1.42 (TPC-DS) at sf40, below the Nebius NIC tier.

### Local SSD as a product option

From [`data-path.md`](../artifacts/comet-research/data-path.md) section 5.

- **(a) Local SSD as the primary store: rare.** Meta replaced Presto Raptor (tables on workers'
  flash) with RaptorX, a cache over the warehouse

  the system of record was found.
- **(b) HDFS on the compute nodes' disks: real on-prem, shrinking.** Uber runs about 1.5 EB of

  ([Uber, 2024-07-30](https://www.uber.com/blog/securing-hadoop-on-gcp), accessed 2026-11-04).

- **(c) Local NVMe as a cache in front of the lake: mainstream.** Databricks' disk cache is on by

## 5. Batched query execution on Comet

Summary of [`batching.md`](../artifacts/comet-research/batching.md).

- **No batch API exists.** Spark shares work only inside one query: exchange and subquery reuse,
  and subplan merging
  ([ReuseExchangeAndSubquery.scala](https://github.com/apache/spark/blob/77bbf77e86ad48f58b5dfbc6ac882b3e70cf1989/sql/core/src/main/scala/org/apache/spark/sql/execution/reuse/ReuseExchangeAndSubquery.scala#L28-L58),
  accessed 2026-11-04). Across queries it shares only through an explicit cache. Comet 1.2.0
  keeps Spark's reuse, and its IR has one root per native block (`operator.proto:32-49`).
- **Ways to submit a batch**, cheapest first (batching.md section 1):
  - **E. Passive sharing in the GPU executor.** No API. Concurrent queries' scan tasks hit one
    column cache keyed by (file, row group, column). On one H100 node all tasks run in one
    executor, so they meet there. Recommended first (estimate).
  - **A. A Spark Connect command plugin** carrying N relations as one unit
    ([Connect.scala](https://github.com/apache/spark/blob/77bbf77e86ad48f58b5dfbc6ac882b3e70cf1989/sql/connect/server/src/main/scala/org/apache/spark/sql/connect/config/Connect.scala#L209-L216),
    accessed 2026-11-04). Add it if E's measured cut falls short.
  - B, a server collecting queries over a window, and C, a Declarative Pipelines run, are middle
    options. D, one plan with many sinks, does not exist in Spark and costs the most.
- **Whole-batch CBO is doable only above Catalyst.** Catalyst, AQE and Comet's rules see one
  query at a time. The optimizer takes N analyzed plans and decides what to share. Its statistics
  are Parquet footers and run history: more than 60% of SCOPE jobs recur
  ([CloudViews](https://www.microsoft.com/en-us/research/wp-content/uploads/2018/03/cloudviews-sigmod2018.pdf),
  accessed 2026-11-04). Spark writes every exchange to completion, so query-fuser's probe-side
  hold becomes "keep the shared scan's chunks until the later stage reads them, or read again".
- **Prior art.** Shared scans pay at high concurrency: QPipe about 2×, MQJoin 2-5×, CJOIN up to
  5× at 32 queries (batching.md section 3, each with its source). Always sharing is not free:
  model-chosen sharing beat always-share by 2.5× on average
  ([Johnson et al., VLDB 2007](https://www.vldb.org/conf/2007/papers/research/p351-johnson.pdf),
  accessed 2026-11-04). At low concurrency shared operators lose to query-at-a-time ones
  ([Psaroudakis et al., VLDB 2013](https://www.vldb.org/pvldb/vol6/p637-psaroudakis.pdf),
  accessed 2026-11-04).
- **How much real ETL shares.** In SCOPE production, CloudViews cut data read by 38.84% (about
  1.6×) and processing time by 38.96%
  ([EDBT 2021, Table 1](https://edbt2021proceedings.github.io/docs/p165.pdf), accessed
  2026-11-04). Almost 40% of daily SCOPE jobs overlap with another
  ([CloudViews, SIGMOD 2018](https://www.microsoft.com/en-us/research/wp-content/uploads/2018/03/cloudviews-sigmod2018.pdf),
  accessed 2026-11-04). That is reuse over time, not shared scans in one window, so 1.6× is a
  production-like case, not a ceiling.
- **TPC batches overstate sharing.** An all-queries TPC batch reads one schema, writes nothing,
  and every query differs: a best case. A batch of 3 to 10 is closer to SCOPE's 1.6×
  (batching.md section 5, estimate). At batch 10 the 8 × 16 mids are 2.17 (TPC-H) and 1.75
  (TPC-DS).

**The NIC under batching** (measured scan bytes over the union of the batch's columns from the
sf40 footers; [`cost.md`](../artifacts/comet-research/cost.md) last table, Task 5 in the
[run state](../tasks/comet-research-detail.md)):

| batch | TPC-H wire GB, alone → shared | cut | per query, shared | TPC-DS wire GB, alone → shared | cut | per query, shared |
|---|---|--:|--:|---|--:|--:|
| 3 | 4.1 → 3.9 | 1.05 | 1.30 | 1.2 → 1.1 | 1.08 | 0.37 |
| 10 | 24.4 → 7.3 | 3.34 | 0.73 | 13.3 → 6.9 | 1.94 | 0.69 |

## 6. The design, and the conditions for a go

Summary of [`design.md`](../artifacts/comet-research/design.md). The verdict is a conditional go,
so it gives both: the alpha design, and what turns it into a go.

### What turns the conditional go into a go

- **Measure, first, without a GPU.** Comet on 16 cores of the CPU VM settles the shuffle rate and
  the scheduling share, the top rows of three cells. Comet at a second scale factor settles the
  fourth (how CPU time grows with size). TPC-DS concurrent "all" from S3 replaces a modelled
  baseline. Both fit in about an hour of the CPU VM (estimate: 16 cores at 8× the 128-core
  times, plus setup); 1.34 h of its 2 h cap is unused.
- **Decode does not appear among the top inputs; GPU speed matters only for TPC-DS sf40.** The
  wire binds first in the batched cells. The GPU speedup moves TPC-H sf40 only between 1.72 and
  1.88, but TPC-DS sf40 between 1.66 and 2.06: its mid stays above 2 only while the speedup is
  above 6.5, against a modelled 10.1 [3.4-28.3]. For TPC-H, a faster GPU buys nothing until the
  wire and the 16-core CPU side do.
- **Hardware and price.** GH200 at $2.29/h clears 2 at mid in every headline cell. Faster feeds
  alone do not.
- **Workload.** The gain grows with the batch's cut. A design partner's real overlap decides
  whether batches look like TPC "all" (cut 5-8) or like SCOPE (about 1.6).
- **The CPU can share too.** If Comet gets the same shared scans, the mids drop 5-26% at sf40 and
  up to 58% at TPC-DS "1 TB" on one 128-core box. Then the case rests on the device factor, which
  has to rise past 1.

### The alpha, by component

- **Seam:** fork Comet 1.2.0's `native/core`. In `PhysicalPlanner::create_plan`, a block with a
  non-empty GPU subtree becomes a `GpuStageExec` over the CPU remainder. JNI and the JVM side stay
  unchanged. One executor per GPU node, 16 cores, tasks sharing the device behind a semaphore.
- **IR and translation:** a protobuf-to-IR translator writing peacockdb's plan nodes straight from
  `spark_operator::Operator`. No DataFusion 55 plan is built for the GPU part. New sources:
  Parquet per task from `object_store`, Arrow from the JVM, Comet shuffle blocks. Adaptations:
  Spark's aggregate buffer layout, sort-merge as hash join, `Expand` as grouping sets, Spark-exact
  arithmetic, cast and decimal rules.
- **Split rule:** [`split.md`](../artifacts/comet-research/split.md)'s, per block. Shuffle stays
  Comet's; the GPU computes murmur3 partition ids (peacockdb's `spark_hash_partition.cu`). Moving
  lz4 to the GPU is the first optimisation the model asks for.
- **Data path and cache:** object-store reads into pinned host buffers, GPU decode with the
  chunked reader, and an executor-level column cache, pinned RAM first, VRAM second, with soft
  affinity so a window's tasks for one file land on one node.
- **Local SSD and exotic tiers:** the cache-in-front-of-the-lake layout, in RAM; NVMe waits for a
  shape where it comes cheap. GH200 is the one exotic tier worth a port (aarch64; the executor
  already runs on GB10).
- **Batching API and CBO:** first no API (passive sharing in the cache, jobs submitted
  concurrently into one long-lived Thrift or Connect server, FAIR scheduling). Then a Connect
  command plugin and a whole-batch CBO above Catalyst, with query-fuser's item 1a hold rule fed by
  run history.

**Size** (estimates, against inventory.md's 22,830-line yardstick): about 10,700 lines reused,
3,800 adapted and 13,800 new. New and adapted together are about 17,600 lines, 0.77× the engine
as it stands. The alpha without the Connect plugin and the CBO is about 14,600.

**The hard part** is not the GPU kernels. It is Spark-exact semantics on the device, per task:
ANSI overflow errors with Spark's messages, Spark's decimal types and cast table, and aggregate
buffers that interoperate with CPU partials across exchanges. A stage must give the same answer
wherever it ran. Second, the 16-core CPU side: shuffle, object-store I/O and broadcast decode run
on 16 cores where the CPU baseline has 128.

**Evidence against** (design.md): no headline cell is a go at mid values; the one-pass floor is
below 1; the GPU numbers are hand-written cuDF pipelines on four TPC-H queries, not the engine;
Comet 1.2.0 is 1.23× faster than 1.1.0 (data-path.md); tasks are small (8192-row batches, a
broadcast rebuilt per task).

| l40s (`gpu-l40s-a`, eu-north1) | 1 h | 0.33 h | 0.38 h | dead-man check 03:07:47-03:13:39 (0.10 h); Experiment 1 03:15:47-03:32:23 (0.28 h) |

- The log undercounts the L40S's first session: its dead-man poweroff closed the use at the last
  heartbeat (03:10:47), while the VM ran until 03:13:39. The wall time includes it.
- **Configurations.** All nine ran in the spec's priority order: TPC-H local sequential (2 runs)
  and concurrent "all" (2 runs); TPC-DS local sequential and concurrent "all" (1 run each); TPC-H
  S3 sequential and concurrent "all"; TPC-DS S3 sequential; and the two in-memory-cache runs
  (TPC-H local, lowest priority). TPC-DS concurrent "all" did not run out of memory, so no
  batch-20 fallback was needed.
- **Nothing was skipped, cut, out of memory or with a scan mismatch.** The S3 runs' plans match
  the local runs' (TPC-H identical; TPC-DS differs only in AQE op counts for q31, q39 and one
  expression id in q35).
- **Two setup failures were fixed in the session:** systemd-logind's `RemoveIPC` deleted the data
  in `/dev/shm` when the last ssh session ended, so a dedicated tmpfs at `/mnt/comet` replaced it;
  and `comet_setup.sh cluster` reported "cluster up" when no daemon had started. Both are in the
  run state.
- **A third bug, found by the audit:** `comet_run.py`'s sequential batch timer also counted
  `--dump-plans` time. The two S3 sequential runs and the two calibration passes used that flag.
  The script is fixed, with a regression test, and the model now takes those two S3 batches as the
  sums of their per-query times, which the dump never touched. No run was repeated.
- **Data.** sf40 Parquet was copied from eu-north1 (TPC-H 42.4 GB at 0.57 GB/s, TPC-DS 15.8 GB at
  0.45 GB/s) and uploaded to the eu-west1 buckets (1.17-1.50 GB/s), every object's size checked.
  The buckets stay; emptying them is the human's call.
- **Every VM used is stopped:** see the end of the [run state](../tasks/comet-research-detail.md)
  "Task 6".
