# Batched query execution on Comet

## Summary
- **Headline:** batching cuts scan bytes over the wire per query by 1.4× (3 queries) to 6.2× (all 22) on TPC-H sf40 (estimate). But production evidence (SCOPE) points to about 1.6×, and Spark with Comet has no way to submit or run a batch as one unit today.
- Spark shares work only inside one query (exchange reuse, subquery reuse, subplan merging). Across queries it shares only through an explicit cache. Comet 1.2.0 keeps exchange reuse, but its plan IR has one root per native block.
- A whole-batch cost-based optimizer is doable only above Catalyst. Its inputs would be Parquet footers and metrics from earlier runs of the same recurring jobs. AQE and Comet's rules see one query at a time.
- The prior art agrees: sharing pays at high concurrency (QPipe, CJOIN, MQJoin 2-5×) and costs extra at low concurrency (Johnson 2007; Psaroudakis 2013).
- For the cost model, use three sharing cases: none (1.0×), production-like (1.6×) and TPC batch (3.4× for 10 random queries, 6.2× for all 22). All three are marked estimate.

## Terms (as in query-fuser)
- **Batch:** N queries run in one window. Sizes 3, 10, 20 and all, as in [query-fuser.md](../../tasks/query-fuser.md).
- **Shared scan:** one read of a table feeding every query in the batch that needs it. It reads the union of the queries' projected columns and of their surviving row groups.
- **Held reader:** a reader of a shared scan behind a join's build, stopped by the join's hold. The fuser either **buffers** it (`GpuHoldBuffer`, costing memory) or **re-reads** it (costing a second load) ([dag-driver.md](../../tasks/dag-driver.md)).
- **Cut:** the bytes a batch reads without sharing, divided by the bytes it reads with sharing.

## 1. The API: how a batch reaches Spark with Comet

### What Spark already shares (Spark 4.1.3, `77bbf77e`, Comet 1.2.0's default build)
- **Exchange and subquery reuse, inside one plan only.** `ReuseExchangeAndSubquery` keys exchanges and subqueries on `canonicalized` plans, in maps created inside each rule call ([ReuseExchangeAndSubquery.scala L28-L58](https://github.com/apache/spark/blob/77bbf77e86ad48f58b5dfbc6ac882b3e70cf1989/sql/core/src/main/scala/org/apache/spark/sql/execution/reuse/ReuseExchangeAndSubquery.scala#L28-L58), accessed 2026-11-04). Both settings default to true (`spark.sql.exchange.reuse`, `spark.sql.execution.reuseSubquery`; [SQLConf.scala L2524-L2536](https://github.com/apache/spark/blob/77bbf77e86ad48f58b5dfbc6ac882b3e70cf1989/sql/catalyst/src/main/scala/org/apache/spark/sql/internal/SQLConf.scala#L2524-L2536), accessed 2026-11-04).
- **AQE's stage cache is per query:** "The exchange-reuse map shared across the entire query, including sub-queries", held in `AdaptiveExecutionContext(session, qe)`, owned by one `QueryExecution` ([AdaptiveSparkPlanExec.scala L949-L960](https://github.com/apache/spark/blob/77bbf77e86ad48f58b5dfbc6ac882b3e70cf1989/sql/core/src/main/scala/org/apache/spark/sql/execution/adaptive/AdaptiveSparkPlanExec.scala#L949-L960), accessed 2026-11-04).
- **CacheManager is the only sharing across queries.** It lives in `SharedState`, which "holds all state shared across sessions" ([SharedState.scala L98](https://github.com/apache/spark/blob/77bbf77e86ad48f58b5dfbc6ac882b3e70cf1989/sql/core/src/main/scala/org/apache/spark/sql/internal/SharedState.scala#L98), accessed 2026-11-04). Caching is explicit (`cacheQuery`); a later plan uses it when a subtree has the same result (`sameResult`) ([CacheManager.scala L65-L133](https://github.com/apache/spark/blob/77bbf77e86ad48f58b5dfbc6ac882b3e70cf1989/sql/core/src/main/scala/org/apache/spark/sql/execution/CacheManager.scala#L65-L133), accessed 2026-11-04).
- **Subplan merging, inside one query.** Started as `MergeScalarSubqueries` (SPARK-34079, `e00b81ee9b`, 2022-04-20); its PR measured TPC-DS q9 50.8 s → 19.5 s ([PR #32298](https://github.com/apache/spark/pull/32298), accessed 2026-11-04). Spark 4.2 renamed it `MergeSubplans` and extended it: SPARK-44571 (`78fcc934d3`, 2025-11-18), filter propagation SPARK-40193 (`f7b4481da1`, 2026-04-21). DSv2 file scans differing only in projected columns now merge into one scan reading the union of columns (`SCAN_MERGING`), the same idea as query-fuser's union projection. Docs report q9 and q28 about 3.5× faster, q88 about 7×, q90 about 2× with symmetric filter propagation, off by default because `OR(f1, f2)` "can therefore read more data" when filters pruned partitions or row groups ([sql-performance-tuning.md, Merging Subplans, @a475424a](https://github.com/apache/spark/blob/a475424a8c56adf84f23e8a6051a385dbb65c50b/docs/sql-performance-tuning.md), accessed 2026-11-04).
- **Concurrent jobs** from separate threads run at once, FIFO by default, FAIR pools optional; nothing in the scheduler shares scans between them ([job-scheduling, Spark 4.1.0](https://spark.apache.org/docs/4.1.0/job-scheduling.html), accessed 2026-11-04).
- **Spark Declarative Pipelines (4.1)** "analyzes the dependencies of your defined objects and orchestrates their order of execution and parallelization"; nothing about shared reads across flows ([SDP guide 4.1.0](https://spark.apache.org/docs/4.1.0/declarative-pipelines-programming-guide.html), accessed 2026-11-04).

- **DataFusion's materialized CTEs arrive too late for Comet 1.2.0.** `WITH ... AS MATERIALIZED` (`MaterializedCteExec`, PR #25580, merge `cdc2fc04`, 2026-10-15) is not in the `55.2.0` tag Comet pins ([PR](https://github.com/apache/datafusion/pull/25580); [Cargo.toml L47](https://github.com/apache/datafusion-comet/blob/ab46419fcc99bcd34aa4d89f7b545d5d51694a88/native/Cargo.toml#L47), accessed 2026-11-04).

### Ways to submit a batch
| Option | How | Shares scans? | Cost and risk |
|---|---|---|---|
| A. Spark Connect command plugin | A custom `Command` carries N relations; `spark.connect.extensions.command.classes` loads a `CommandPlugin` ([Connect.scala L209-L216](https://github.com/apache/spark/blob/77bbf77e86ad48f58b5dfbc6ac882b3e70cf1989/sql/connect/server/src/main/scala/org/apache/spark/sql/connect/config/Connect.scala#L209-L216), accessed 2026-11-04) | Only if the plugin plans the N queries together (D or E) | Client change plus a server jar. Cleanest explicit API (estimate). |
| B. Planner collecting queries over a window (Thrift or Kyuubi sessions) | Server holds statements up to T seconds, then plans them together | Same as A | Adds latency up to T; custom server. ETL jobs that "trigger all jobs at the start of every period" fit (EDBT 2021 §4). |
| C. Declarative Pipelines run | One pipeline with many flows | Not today | Already one unit, a natural place for a shared-read pass (estimate). |
| D. One plan with many sinks | No multi-sink plan or multi-output map stage exists in Spark (one `ShuffleDependency` per map stage; estimate from Spark's design). A tagged `UNION ALL` with a custom writer can fake it | Yes, inside one job | Spark core work or a fragile hack; Comet's IR needs a multi-root node. Highest cost (estimate). |
| E. Passive sharing in the GPU executor | No API. Concurrent queries' scan tasks hit a shared column cache with read coalescing, keyed by (file, row group, column), as in Db2 scan sharing and cooperative scans | Yes, when queries overlap in time and the cache holds the window's data | Lowest cost. On one H100 node all tasks run in one executor, so they meet there. Needs FAIR scheduling and enough RAM (estimate). |

- **Recommendation (estimate):** build E first; it needs nothing from Spark and gives the scan-sharing part of the cut. Add A only if E's measured cut falls short.
- **D is the only way to fuse operators above the scan** (query-fuser's mergeable subtrees). In Spark it costs the most.

## 2. Whole-batch cost-based optimization with Comet
- **Where it can sit.** Catalyst, AQE and Comet's rules all work one `QueryExecution` at a time; Comet's rules run inside Spark's `ApplyColumnarRulesAndInsertTransitions` and AQE stage preparation ([CometSparkSessionExtensions.scala L44-L80](https://github.com/apache/datafusion-comet/blob/ab46419fcc99bcd34aa4d89f7b545d5d51694a88/spark/src/main/scala/org/apache/comet/CometSparkSessionExtensions.scala#L44-L80), accessed 2026-11-04). A batch optimizer must sit **above** them: take N analyzed logical plans, decide what to share, then (i) for E, hint the executor cache which (file, column) chunks to keep, or (ii) for A/D, rewrite the batch into one plan and let Catalyst, AQE and Comet's serializer run as usual below.
- **Below the serializer is too late.** The GPU executor sees one native block per task from one query. Fusing across queries there means making tasks from N Spark jobs meet on one executor, which Spark's scheduler does not guarantee (estimate).
- **Probe-side holds in Spark.** Spark writes every shuffle and broadcast to completion before the stage that reads it, so a join's probe input never waits on a pipe the way peacockdb's held readers do. "Buffer vs re-read" becomes "persist the shared scan's output (cache or shuffle) vs scan again in the later stage" (estimate). Inside one stage on the GPU executor, query-fuser's rule applies as is.
- **Statistics the batch optimizer would have:**

| Source | What it gives | Limits |
|---|---|---|
| Parquet footers | Exact compressed bytes per column chunk, row counts, min/max per row group (the inputs of §6) | Nothing about selectivity above the scan |
| Catalog statistics (`ANALYZE TABLE ... FOR COLUMNS`) | Row counts, distinct values, histograms | `spark.sql.cbo.enabled` and `joinReorder` default to false ([SQLConf.scala L3625-L3643](https://github.com/apache/spark/blob/77bbf77e86ad48f58b5dfbc6ac882b3e70cf1989/sql/catalyst/src/main/scala/org/apache/spark/sql/internal/SQLConf.scala#L3625-L3643), accessed 2026-11-04); often missing |
| AQE runtime statistics | Real shuffle sizes per stage | Only after a stage runs, inside one query; too late for a pre-batch decision |
| Earlier runs of recurring jobs (SQL metrics, event logs) | Per-operator rows and bytes, the analog of query-fuser's sf40 `batch_bytes` | Most ETL recurs: more than 60% of SCOPE jobs ([CloudViews §1.3](https://www.microsoft.com/en-us/research/wp-content/uploads/2018/03/cloudviews-sigmod2018.pdf), accessed 2026-11-04); CloudViews' and SparkCruise's feedback loop |

- **Verdict:** doable as a layer above Spark using footers and run history; not doable inside Comet's serializer. Its buffer-or-re-read rule can reuse query-fuser's, with history in place of the sf40 files (estimate).

## 5. TPC-H and TPC-DS as stand-ins for ETL
- **No table is read by every query.** Method: column names in each query's SQL matched against the Parquet schemas (estimate), using `testdata/tpch-queries/` and `testdata/tpcds-queries/` at repo `f4e2767d`. TPC-H: lineitem 17 of 22, orders 12, supplier 10, nation 9, part 8, customer 8, partsupp 5, region 3; 3.3 tables per query on average. TPC-DS (99): date_dim 89, store_sales 67, item 52, catalog_sales 39, web_sales 36, store 34; 4.9 tables per query.
- **Bytes are concentrated.** Repo sf1 Parquet (DuckDB 1.5.4, `testdata/generate_testdata.sh` @ f4e2767d): TPC-H lineitem 207.6 of 382.9 MB (54%), partsupp 94.1, orders 55.3. TPC-DS store_sales 154.5, catalog_sales 119.8, web_sales 58.8 of 413.3 MB.
- **Distinct table sets.** TPC-H 16 in 22 queries; TPC-DS 66 in 99. Redshift found an average of only 23.5 distinct table sets in more than 50,000 queries per cluster (max 108), across 10 clusters ([VLDB 2024 §4.5](https://vldb.org/pvldb/vol17/p3694-saxena.pdf), accessed 2026-11-04). Real workloads concentrate on fewer sets, which helps sharing.
- **Real ETL writes much more.** In the Redshift fleet SELECTs are 48.9% of queries but 28.6% of runtime; COPY 38.3%, CTAS 16.4% (Table 2). In TPC-H/DS selects are about 90% of runtime. About 80% of queries are exact repeats in 50% of clusters (§1, §4.4), which suits result caching, not batching (accessed 2026-11-04).
- **Operator mix differs.** TPC-DS has more than 3× the share of joins of production Spark (18.9% vs 5.3%) and a third of the aggregates (6.5% vs 18.8%) ([SparkCruise §7](https://www.vldb.org/pvldb/vol14/p3122-roy.pdf), accessed 2026-11-04).
- **Verdict (estimate):** an all-queries TPC batch is a best case for sharing (one schema, every query differs, nothing written). A random batch of 3 to 10 TPC queries is closer to SCOPE's production cut.

## 6. The NIC under batching
**Method (estimate).** C(q) = Parquet columns query q reads; s(c) = a column's compressed bytes from the footers. Unshared U = Σ_{q∈B} Σ_{c∈C(q)} s(c); shared S = Σ_{c∈∪C(q)} s(c); cut = U/S; wire bytes per query = S/N. This matches query-fuser's union projection. Row-group pruning ignored; a column counted once per query even when scanned twice. Sizes = sf1 footers × 40; NIC time at 5 GB/s (40 Gbit/s). Two query orders shown: numeric and alphabetical (q1, q10, q11, …); query-fuser's real order comes from `cases.csv`, not in this tree. Also the median and p10-p90 over 2,000 random batches.

**TPC-H sf40 (estimate; 15.3 GB of Parquet total):**

| Batch | Unshared → shared bytes | Per query | Cut, numeric (alphabetical) | Random cut, median (p10-p90) | Wire time per batch at 5 GB/s |
|---|---|---|---|---|---|
| 3 | 5.2 → 3.8 GB | 1.73 → 1.27 GB | 1.36× (1.33×) | 1.45× (1.04-1.97) | 1.0 → 0.8 s |
| 10 | 29.5 → 6.5 GB | 2.95 → 0.65 GB | 4.53× (2.35×) | 3.38× (2.70-4.14) | 5.9 → 1.3 s |
| 20 | 48.2 → 8.3 GB | 2.41 → 0.41 GB | 5.82× (4.97×) | 5.69× (5.36-6.11) | 9.6 → 1.7 s |
| all 22 | 51.1 → 8.3 GB | 2.32 → 0.38 GB | 6.16× | 6.16× | 10.2 → 1.7 s |

**TPC-DS sf40 (estimate; 99 queries; query-fuser's "all" is the 82 that pass at sf40):** numeric order cut 1.02× (3), 1.55× (10), 2.33× (20), 7.45× (99); random median 1.13×, 1.69×, 2.41×, 7.45×. All 99: 102.3 → 13.7 GB, 1.03 → 0.14 GB per query.

**What it means (estimate):**
- With sharing, a TPC-H batch's wire bytes stop growing at about 8.3 GB (the union of used columns, 54% of the dataset); after that per-query bytes fall as 1/N.
- Decode and PCIe bytes fall by the same cut, because query-fuser shares the load and decode as well as the read.
- **Against a cluster of small nodes:** GPU-node wire time per query ÷ cluster's = (S/U) × (k·R_small / R_gpu). With k = 8 small nodes each with the GPU node's NIC rate, the GPU node needs a cut of at least 8× just to tie on the wire. TPC-H's best case is 6.2×. Real NIC rates come from data-path.md.

## 7. Evidence against batching paying off
- **Small batches share little:** 3 random queries give a median 1.45× (TPC-H) and 1.13× (TPC-DS) (estimate, §6).
- **Production sharing is about 1.6×, not 6×** (EDBT 2021, Table 1); 46% of overlaps cost 1% or less of their query (CloudViews 2018, §2.4).
- **Unions lose pruning.** In peacockdb's sf40 trace q6 loads row groups 543-840: 298 of the 1,954 that q19 loads (`testdata/benchmark-results/tpch.sf40/tp1_single.benchmark.txt` @ f4e2767d, measured earlier). Fused with q1, q6 reads all of them. Spark's docs warn `OR(f1, f2)` "can therefore read more data" (accessed 2026-11-04). A shared scan can also defeat DPP and runtime filters ([vecruntime #637](https://github.com/vecruntime/vecruntime/issues/637), accessed 2026-11-04).
- **Sharing costs extra at low concurrency:** always-share was 2.5× worse than model-chosen sharing (Johnson 2007); shared operators lose to query-centric ones at low concurrency (Psaroudakis 2013).
- **Latency gains are uneven:** CloudViews median per-job latency −15% vs −34% cumulative (EDBT 2021, §3.2); 6 of 32 jobs used more PN hours (2018, §7.1).
- **ETL time is mostly writes:** COPY and CTAS take 54.7% of Redshift runtime (VLDB 2024, Table 2). Batching shares only reads.
- **No API, one-root IR.** Spark has no multi-sink plan; AQE's stage cache is per query; Comet's IR has one root per block, and Spark 4.2's merging already causes a Comet fallback (§1). Everything except option E is Spark-level work, outside Comet.
- **The CPU can batch too.** Shared scans are software: Comet on CPU could cache a batch's columns in its Arrow cache and get the same byte cut. Against such a baseline batching does not move the GPU/CPU ratio (estimate). The bar's CPU runs (experiment 2) do not share scans across queries, so the report must say so.
- **Memory.** Held readers and caches cost VRAM (80 GB) or host RAM (about 200 GB). TPC-H sf40's 8.3 GB union fits; real ETL tables often do not, and then sharing needs scans scheduled together, not just a cache (estimate).
- **Spark applications are small:** most have fewer than 10 queries (SparkCruise, Fig. 4c), so a batch must span applications and users. Customers resisted changing submission schedules (EDBT 2021, §4).

**Evidence for:** concurrent opportunities are common ("thousands" a day in Cosmos, EDBT 2021 §5.4); systems built for sharing report 2-5× at high concurrency (QPipe, MQJoin, CJOIN); Spark 4.2 merges scans inside a query by default; on one H100 node every task runs in one executor, so passive sharing (E) needs no Spark change.

## Follow-up experiments
1. Re-run §6 on query-fuser's real batch order and surviving row groups (chain L's `cases.csv` and fused `reads per table`); compare modelled shared bytes with measured fused load bytes.
2. A fair CPU baseline for batching: Comet on the 128-core VM with `spark.comet.exec.inMemoryCache.enabled=true`, caching each batch's union of columns, vs sequential and concurrent runs. Settles whether batching moves the GPU/CPU ratio at all.
3. Loss of row-group pruning: per TPC-H/DS query at sf40, record surviving row groups alone and in the batch union; recompute the cut with f(q, c) < 1.
4. Passive-sharing simulation (option E): replay N concurrent queries' column-chunk requests under FAIR scheduling; report cache hit rate and NIC bytes vs cache size (10, 50, 200 GB).
5. Spark Connect batch command prototype: plan N relations in one `CommandPlugin` call; check whether their scan tasks overlap in time on one executor and how far AQE's per-query planning shifts them apart.
6. A real ETL trace: one design partner's Spark event logs, SparkCruise-style; compute access sets, overlap per window and the cut, to replace the TPC and SCOPE factors in the cost model.
